# Review rubric

Apply the hard gates first. Score only designs that pass them.

## Hard gates

Reject or require revision when any condition holds:

1. The target entity or task is undefined.
2. Training or tuning uses the formal test set.
3. Upstream predictions used for downstream training are in-sample when deployment predictions are out-of-sample.
4. Ground-truth-derived fields enter inference.
5. Failure, abstention, empty input, or retry cases disappear from the denominator.
6. The design assumes an unavailable artifact, API, probability map, model interface, or label.
7. A high-confidence prediction is forced when the required evidence is absent.
8. The exact requested Pro model was not verified in the UI.
9. Compute is unbounded or hides multiplicative nested fits.
10. Cross-module field definitions conflict.

## Evidence tiers

| Tier | Meaning |
|---|---|
| Direct | Same task, modality/domain, failure mechanism, and comparable input contract |
| Transferable | Different domain or task but the same technical failure mechanism |
| Conceptual | General architecture or theory without validating this deployment failure |
| Unsupported | Memory, blog, vague citation, or architecture intuition only |

Require the recommendation to state when its central novelty has only transferable or conceptual evidence.

## Generic 100-point review

| Category | Points |
|---|---:|
| Problem and target definition | 10 |
| Evidence quality and literature accuracy | 15 |
| Leakage-safe data and evaluation design | 15 |
| Architecture attribution and baselines | 15 |
| Failure realism and safety behavior | 15 |
| Interface and inference correctness | 10 |
| Calibration, uncertainty, or abstention validity | 5 |
| Compute and sample-size feasibility | 10 |
| Implementation clarity | 3 |
| Defensible novelty | 2 |

Interpretation:

- 85–100: conditional accept; implement behind stated gates.
- 70–84: revise; promising but blockers remain.
- 50–69: restart with a simpler design.
- below 50: reject the direction.

## Over-design checks

Count:

- learned modules;
- loss terms;
- tuned thresholds;
- calibration models;
- expert branches;
- separate seeds and folds;
- upstream fits multiplied by downstream folds;
- fields that require new data or annotation.

Demand staged evidence before retaining a new module. Prefer:

```text
baseline
→ corruption/data fix
→ smallest learned extension
→ complex branch only if a prespecified residual failure remains
```

## Leakage and statistics checks

Verify:

- group or entity assignment precedes all splits;
- every training input is generated by an upstream model that excluded that entity when OOF behavior is required;
- architecture selection, threshold fitting, calibration, and final testing have distinct roles;
- the test remains sealed until all hashes and thresholds are frozen;
- multiple variants from one entity are not counted as independent;
- adaptive threshold selection uses a selection-valid procedure;
- confidence intervals and paired comparisons use the correct entity level;
- results without a sealed cohort are labeled development-only.

## Interface audit

For every field, record:

```text
name
producer
consumer
unit
shape
allowed values
missing-value rule
training definition
inference availability
version
```

Flag:

- one name with two thresholds;
- probabilities used as calibrated when they are only ranking scores;
- different coordinate spaces;
- a downstream retry that bypasses upstream ordering;
- duplicate abstention systems;
- final refits that change the downstream input distribution;
- job counts reported separately but added in the integrated study.

## Acceptance decision

Write:

```text
DECISION: ACCEPT | CONDITIONAL ACCEPT | REVISE | RESTART | REJECT
SCORE: <n>/100
HARD GATES: <pass/fail>
BLOCKERS: <short list>
RETAIN: <strong parts>
NEXT PROMPT: <focused revision scope or none>
```

Do not accept a design because it is long, cites many papers, or assigns itself a high score.
